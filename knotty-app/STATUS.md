# IshuriHUB — Project Status

_Last updated: 30 Oct 2026_

## What this is

A **Next.js 16 frontend** for an NFC card-based smart school management system, aimed at
Rwandan schools (currency is RWF, phone formats are `+250`, grades are "Senior 3–6",
curriculum references REB Rwanda).

The central idea: every student and worker carries an NFC card. Tapping that card drives
attendance, gate access, canteen purchases, library loans, fee payments, discipline
records, and clinic visits. Where real NFC hardware isn't available, a "Virtual Card Tap"
fallback simulates the same flow.

This repository is **frontend only**. The backend lives in a separate project and is
reached over HTTP.

## Stack

| Layer | Choice |
| --- | --- |
| Framework | Next.js 16.2.7, App Router, React 19.2.4 |
| Styling | Tailwind CSS v4 (via `@tailwindcss/postcss`) |
| Icons | `lucide-react` |
| Charts | `recharts` |
| NFC | Web NFC (`NDEFReader`) + `html5-qrcode` for barcode fallback |
| Language | TypeScript 5 |
| Dev server | `npm run dev` → `next dev --webpack -H 0.0.0.0` |

Note that dev runs on **Webpack, not Turbopack**, and binds to `0.0.0.0` — almost
certainly so a real Android phone on the same network can reach the dev server to test
Web NFC, which only works in Chrome on Android.

## What's built

### Routes (21 pages under `app/`)

**Shared / staff-facing**
`/` (role-dispatched dashboard), `/login`, `/students`, `/students/[id]`, `/workers`,
`/schools`, `/attendance`, `/gate-access`, `/library`, `/materials`, `/reports`,
`/discipline`, `/health`, `/cards`, `/canteen`, `/fees`, `/standalone-tap`, `/settings`

**Student / parent self-service**
`/my-profile`, `/my-attendance`, `/my-reports`, `/my-card`

### Role system

Nine primary roles — `ADMIN`, `TEACHER`, `STUDENT`, `PARENT`, `NURSE`, `BURSAR`,
`DISCIPLINE`, `CANTEEN`, `LIBRARIAN` — plus four "management" roles treated as
Admin-equivalent in `lib/roles.ts`: `SCHOOL_MANAGER`, `ORGANIZATION_MANAGER`,
`PLATFORM_ADMIN` (and `ADMIN` itself).

Access control happens in two places:

- `components/Sidebar.tsx` holds a single `ALL_NAV` array where each entry declares the
  roles allowed to see it. Nav is filtered client-side.
- `app/page.tsx` dispatches to one of seven role dashboards in
  `components/dashboards/`, lazy-loaded via `next/dynamic`. `LIBRARIAN` has no dashboard
  and is redirected to `/library` instead.

### API layer

`lib/api.ts` is a single file exposing **21 namespaces**: `auth`, `schools`, `structure`,
`students`, `attendance`, `cards`, `fees`, `canteen`, `discipline`, `health`,
`achievements`, `reports`, `materials`, `myAccount`, `notifications`, `teachers`,
`library`, `gateAccess`, `academics`, `workers`, `multiSchool`.

It also owns the access/refresh token cycle, non-JSON response detection, and session
teardown with redirect to `/login`.

### PWA

`public/manifest.json` + `public/sw.js`, registered by
`components/ServiceWorkerRegistrar.tsx`. Installable, standalone display, portrait-locked,
with home-screen shortcuts to Attendance, Canteen, and Health.

### Contexts

`context/AuthContext.tsx` (session, active school, school switching),
`context/ThemeContext.tsx`, `context/ToastContext.tsx`.

## Open issues

These are the things most likely to bite next. Listed roughly by how much they matter.

### 1. Login accepts any credentials

In `context/AuthContext.tsx`, when the backend auth call fails, `login()` catches the
error and **fabricates a valid local session instead of rejecting**. If the email isn't in
`DEMO_ACCOUNTS`, it infers a role by substring-matching the email prefix and defaults to
`ADMIN`:

```ts
: prefix.includes("student") ? "STUDENT"
: prefix.includes("worker")  ? "WORKER"
: "ADMIN";
```

So with the backend down or unreachable, `anything@anything.com` with any password logs in
as a full administrator. This is fine as a demo affordance and dangerous as a shipped
default — it needs to be gated behind an explicit flag before any real deployment.

### 2. Three different backend URLs

Nothing agrees on where the API lives:

| Source | Value |
| --- | --- |
| `wrangler.toml` → `NEXT_PUBLIC_API_URL` | `https://ishuri-hub-backend.workers.dev` |
| `next.config.ts` → production `BACKEND_URL` | `https://knotty-backend.vercel.app` |
| `next.config.ts` → development `BACKEND_URL` | `http://127.0.0.1:5000` |
| `.env.local` → `NEXT_PUBLIC_API_URL` | `/api/v1` |

Worth deciding which is canonical and deleting the rest.

### 3. Two deploy targets configured at once

`wrangler.toml` targets Cloudflare Pages (`pages_build_output_dir = ".next"`,
`nodejs_compat`), and `public/_redirects` is a Cloudflare-style SPA fallback
(`/* /index.html 200`). Meanwhile the `.env` files were generated by the Vercel CLI and
point at a Vercel project named `knotty-app`. `next.config.ts` switches to
`output: "export"` when `CF_PAGES=1` or `OUTPUT_EXPORT=1`, which also disables the
`/api/*` and `/uploads/*` rewrites — so the static-export path and the rewrite path are
mutually exclusive and the app behaves differently depending on which one runs.

### 4. The rebrand from "Knotty" to "IshuriHUB" is half-done

Both names are live across the codebase:

- `package.json` is `ishuri-hub`; the directory is `knotty-app`.
- `lib/api.ts` reads and writes **every** localStorage key under both `ishuri_` and
  `knotty_` prefixes for backwards compatibility.
- `components/KnottyCard.tsx` and the exported `KnottyCard` type still carry the old name.
- Card numbers in UI placeholders use the old `KNT-` prefix
  (e.g. `KNT-KMS-2026-00001`, `KNT-8492-1001`).

Finishing this means picking one prefix, writing a one-time migration, and dropping the
dual-write.

### 5. `lib/api.ts` is a 5,000-line, 200 KB monolith

Every type and every endpoint for all 21 namespaces sits in one file. It's the obvious
candidate for a split into `lib/api/<namespace>.ts` with a shared `request` core.

### 6. `WORKER` role falls through to a blank dashboard

The login fallback can assign a `WORKER` role, but `WORKER` appears nowhere in
`ALL_NAV`, nowhere in `ROLE_LABELS`, and in no branch of the dashboard dispatch in
`app/page.tsx`. Because it also isn't a management role, a `WORKER` login renders an empty
shell. Either add the role properly or stop emitting it.

### 7. The README is still the `create-next-app` default

No setup steps, no env var documentation, no mention of the backend dependency or the
Android/NFC testing requirement.

## Not verified

Be aware that the following could not be checked, because **shell commands return no exit
status in this environment** — every `git` invocation failed silently:

- Current branch, uncommitted changes, and commit history.
- Whether the project builds (`npm run build`) or passes lint.
- Whether the backend is reachable, and therefore whether the app is currently running
  against real data or the `lib/demo.ts` fallback.

Re-run these manually before trusting any of the above as a current snapshot.

A note on credentials: `.env.local`, `.env.prod`, and `.env.production.local` each contain
a `VERCEL_OIDC_TOKEN`. All three are short-lived and already expired, and `.gitignore`
covers `.env*`, so they are not committed — no action needed, just don't paste them
anywhere.

## Suggested next steps

1. Gate the demo-login fallback behind an explicit env flag so it can't ship as the
   default auth path.
2. Settle on one backend URL and one deploy target; delete the losing configuration.
3. Finish the `knotty_` → `ishuri_` rename and remove the dual-write.
4. Resolve or remove the `WORKER` role.
5. Split `lib/api.ts` by namespace.
6. Replace the default README with real setup instructions, including how to test NFC on
   an Android device against the `0.0.0.0` dev server.
